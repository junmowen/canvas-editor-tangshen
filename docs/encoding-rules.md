# 项目编码与注释强制约束

## 1. 强制编码规则

项目内所有文本文件必须满足以下要求：

- 编码：**UTF-8（无 BOM）**
- 换行：**LF**
- 禁止提交乱码内容
- 禁止提交 BOM
- 禁止混用 CRLF / CR / LF

适用文件类型包括但不限于：

- `*.ts`
- `*.tsx`
- `*.js`
- `*.jsx`
- `*.mjs`
- `*.cjs`
- `*.json`
- `*.md`
- `*.html`
- `*.css`
- `*.scss`
- `*.less`
- `*.yml`
- `*.yaml`
- `*.svg`
- `*.txt`

---

## 2. 中文注释强制规则

从现在开始，项目内新增或修改的核心逻辑，必须补充**可读、准确、直接的中文注释**。

### 2.1 必须补充中文注释的场景

以下内容必须写中文注释：

- 新增函数
- 新增类
- 新增方法
- 新增复杂变量
- 新增关键属性
- 新增条件分支
- 新增循环逻辑
- 新增边界处理
- 新增兼容/分页/坐标/选区相关逻辑
- 旧逻辑重构后语义发生变化的位置

### 2.2 中文注释要求

中文注释必须满足：

- 直接说明“这段逻辑在做什么”
- 必要时说明“为什么这么做”
- 必要时说明“边界条件是什么”
- 注释内容必须与代码真实行为一致
- 禁止空洞注释
- 禁止复制粘贴无意义注释
- 禁止乱码注释

错误示例：

- `// 处理`
- `// 逻辑`
- `// TODO`
- `// fix`
- 乱码注释

正确示例：

- `// 将鼠标命中位置统一转换为选区边界索引，避免字符索引与边界索引混用`
- `// 当前命中的是分页单元格首行左侧空白区，此时光标应落到行首边界`
- `// 只有起止单元格不同时才视为跨行跨列选区，单元格内光标闭合不属于跨单元格选择`

---

## 3. 函数注释规则

所有新增函数、方法，原则上都要有函数级中文注释。

推荐格式：

```ts
/**
 * 说明函数职责。
 * 说明输入输出。
 * 说明关键边界或特殊约束。
 */
```

至少应说明：

- 函数用途
- 输入参数语义
- 返回值语义
- 是否涉及分页、坐标、选区、边界、缓存、渲染

---

## 4. 变量与属性注释规则

以下变量或属性必须补中文注释：

- 含义不直观的索引
- 边界索引
- 分页相关索引
- 逻辑态 / 布局态 / 渲染态字段
- 临时补偿变量
- 偏移量
- 缓存变量

推荐示例：

```ts
// 逻辑选区左边界索引，遵循 (startIndex, endIndex] 语义
const selectionStartBoundary = ...

// 当前分页片段内的本地边界索引
const localBoundaryIndex = ...
```

---

## 5. 行内关键注释规则

以下情况必须在关键行旁边写中文注释：

- 兼容特殊分支
- 纠正 off-by-one
- ZERO 占位符处理
- 分页片段首尾边界处理
- 表格跨页跳转
- 复制与高亮共用逻辑
- 光标位置修正
- 渲染区间裁剪

---

## 6. 命名约束

涉及选区、分页、坐标、边界的命名必须优先使用**语义化命名**，禁止继续堆积历史歧义命名。

优先使用：

- `boundary`
- `selection`
- `logical`
- `layout`
- `fragment`
- `local`
- `absolute`

禁止新增模糊命名：

- `tmp`
- `fixData`
- `newData`
- `idx2`
- `testVar`
- `cache2`

---

## 7. 修改约束

以后所有改动都必须遵守以下顺序：

1. 先保证编码正确
2. 再修改逻辑
3. 修改时补中文注释
4. 不允许先改逻辑后补注释
5. 不允许提交乱码注释

---

## 8. 提交前检查

提交前必须至少检查：

```bash
npm run encoding:check
```

如需扫描整个仓库：

```bash
npm run encoding:check:all
```

如编码、换行、注释不符合规则，必须先修复，再继续开发。

---

## 9. 本项目后续强制执行要求

从本文件更新后开始，后续所有新增或修改代码必须遵守：

- 不允许再出现乱码中文
- 不允许省略中文注释
- 不允许新增无语义历史字段命名
- 不允许在核心逻辑里写无说明代码
- 不允许提交 UTF-8 BOM
- 不允许提交 CRLF

---

## 10. 说明

- 终端看到乱码，不一定代表文件本身编码错误，也可能是终端代码页显示问题
- 以编辑器实际编码、Git 工作树和 `encoding:check` 结果为准
- 若文件出现乱码，优先先修编码和中文注释，再处理功能逻辑
