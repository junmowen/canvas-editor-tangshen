# Canvas Editor 上游 Issues 使用方案

## 1. 目的

这份文档不是给仓库作者做 issue 治理，而是给个人使用者用的。

目标只有一个：

> 利用上游 GitHub issues 信息，降低自己在 `canvas-editor` 上的使用风险，并优化本地接入策略。

适用场景：

1. 你不是仓库维护者
2. 你不打算去管理对方仓库的 labels、milestones、模板
3. 你只想从上游 issues 中提取“哪些坑要避开、哪些功能不稳定、升级前要检查什么”

---

## 2. 当前上游信息基线

基于 `2026-04-27` 查看的 GitHub 公开页面：

1. 仓库 open issues 为 `50`
2. 当前存在较多 table / pagination / cursor / render 相关问题
3. 上游 issue 模板主要还是 bug 和 feature 两类

来源：

- Issues: <https://github.com/Hufe921/canvas-editor/issues>
- Labels: <https://github.com/Hufe921/canvas-editor/labels>

这说明一件事：

> 这个项目功能很多，但核心编辑链路仍在持续演进，不能按“稳定成品组件”去盲目升级和接入。

---

## 3. 个人使用者最该关心什么

你不需要关心“如何整理作者的 issue 池”，你真正该关心的是下面四类信息：

### 3.1 哪些能力仍在高风险区

从当前 issue 与仓库内重构文档看，高风险区主要是：

1. 表格
2. 分页
3. 光标
4. 选区
5. 命中测试
6. 图片环绕
7. 性能

这些能力不是不能用，而是：

1. 升级时最容易被影响
2. 使用时最需要预设约束
3. 最值得做本地回归

### 3.2 哪些功能需求还只是“想法”，不是稳定能力

当前 open issues 里能看到不少功能诉求，例如：

1. 表格按内容自动调整
2. 同屏多页
3. 分栏
4. Area 插入表格

这类内容不能当成“近期一定可用”的能力去设计你的产品。

更合理的做法是：

1. 先把它当 backlog
2. 不把业务强依赖建立在这些能力上
3. 必要时自己做本地扩展或备用方案

### 3.3 哪些已知问题会影响你的业务场景

你要筛的不是“所有 issue”，而是：

1. 会不会影响你的页面模式
2. 会不会影响你的输入模型
3. 会不会影响你的控件和表格
4. 会不会影响你的导出和打印

### 3.4 版本升级前要查哪些 issue

升级前最该查的不是所有 open issues，而是：

1. 最近新开的 bug
2. 与你使用模块相关的 open issues
3. 与你当前版本相邻的回归问题

---

## 4. 建议的个人 issue 使用方法

## 4.1 建立自己的 issue 关注清单

建议你不要直接看完整 issue 列表，而是固定关注以下专题：

1. 表格与分页
2. 光标与选区
3. 渲染与图片
4. 性能

最简单的做法是保存 GitHub 搜索链接。

建议收藏：

1. `is:issue is:open table`
2. `is:issue is:open pagination`
3. `is:issue is:open cursor`
4. `is:issue is:open selection`
5. `is:issue is:open image`
6. `is:issue is:open performance`

使用方式：

1. 每次准备升级前看一遍
2. 每次准备启用新能力前看一遍

---

## 4.2 把 issue 分成三类，而不是全都同等对待

建议你自己本地做一个轻量分类：

### A 类：会影响当前业务

判断标准：

1. 你正在使用这个能力
2. bug 会直接影响业务正确性
3. 没有明显绕过方案

这类 issue 要做的事：

1. 记录 issue 链接
2. 写本地回归样例
3. 升级前专项验证

### B 类：会影响未来规划

判断标准：

1. 你准备使用这个能力
2. 当前 issue 显示它仍不稳定
3. 你还没有必须马上上线

这类 issue 要做的事：

1. 现阶段不作为强依赖
2. 保留替代方案
3. 等 issue / 文档 / release 更明确后再接入

### C 类：仅做背景信息

判断标准：

1. 不是你的业务范围
2. 短期不会使用
3. 对当前接入没有影响

这类 issue 不要花太多时间。

---

## 4.3 建议你本地维护一份“已知风险表”

你不需要改上游仓库，但应该在自己项目里维护一份风险表。

建议字段：

1. `能力`
2. `是否在用`
3. `关联 issue`
4. `影响范围`
5. `规避方式`
6. `升级前是否必测`

例如：

| 能力 | 是否在用 | 关联 issue | 风险判断 | 当前策略 |
| --- | --- | --- | --- | --- |
| 表格分页 | 是 | `#41` | 高 | 升级必测，限制复杂嵌套用法 |
| 表格缺省列宽 | 是 | `#1404` | 已本地验证 | 已补缺省 `colgroup` 回归，升级保留必测 |
| 表格前插入内容 | 是 | `#1163` | 高 | 使用前先做回归样例 |
| 控件删除 | 是 | `#1399` | 中 | 避免重度依赖 CONTROL 选中删除 |
| 图片环绕 | 否 | `#1200` `#1372` | 中 | 暂不用于核心业务 |
| 同屏多页 | 否 | `#1270` | 低 | 不纳入当前设计 |

## 5. 当前最值得你重点关注的 issue 方向

以下不是“作者应该怎么排期”，而是“你作为使用者最该小心哪些方向”。

## 5.1 表格与分页

当前应优先关注：

1. [#41](https://github.com/Hufe921/canvas-editor/issues/41) 表格分页
2. [#1404](https://github.com/Hufe921/canvas-editor/issues/1404) `colgroup` 默认宽度（本地已补缺省 `colgroup` 回归）
3. [#1163](https://github.com/Hufe921/canvas-editor/issues/1163) 表格前添加文字
4. [#1387](https://github.com/Hufe921/canvas-editor/issues/1387) 根据内容自动调整表格
5. [#1317](https://github.com/Hufe921/canvas-editor/issues/1317) Area 插入表格

对个人使用的含义：

1. 如果你业务强依赖表格，不要直接假设 table 行为已经完全稳定
2. 表格前后插入内容、分页、自动宽度这类边界要自己补样例
3. 尽量先用更保守的表格配置

## 5.2 光标、删除、选区

当前应优先关注：

1. [#813](https://github.com/Hufe921/canvas-editor/issues/813) 光标位置
2. [#1399](https://github.com/Hufe921/canvas-editor/issues/1399) CONTROL 选中后 backspace 无效

对个人使用的含义：

1. 如果你的业务使用大量控件和复杂选区，必须自己补交互回归
2. 输入、删除、左右移动、拖选是升级时最高优先级必测项

## 5.3 渲染与图片

当前应优先关注：

1. [#1385](https://github.com/Hufe921/canvas-editor/issues/1385) 下划线显示异常（本地已补控件下划线回归）
2. [#1372](https://github.com/Hufe921/canvas-editor/issues/1372) 图片浮动文字之上
3. [#1200](https://github.com/Hufe921/canvas-editor/issues/1200) 图片环绕

对个人使用的含义：

1. 文本装饰和图片环绕不要直接当成已完全稳定的排版能力
2. 如果你的业务是文档模板、海报、报告类编辑，必须单独验这个方向

## 5.4 暂不建议当成近期可靠能力的需求

建议先不要重度依赖：

1. [#1270](https://github.com/Hufe921/canvas-editor/issues/1270) 同屏多页
2. [#1237](https://github.com/Hufe921/canvas-editor/issues/1237) 分栏
3. [#1256](https://github.com/Hufe921/canvas-editor/issues/1256) 日期年/月自定义

原因不是它们不好，而是：

1. 这些更像 roadmap 或功能诉求
2. 不适合当成你当前产品设计的确定输入

## 6. 推荐的本地接入策略

## 6.1 给高风险能力包一层业务适配层

如果你在自己的项目里直接到处调用 editor API，后面会很难控风险。

更合理的做法是：

1. 把表格操作封装成自己的业务 API
2. 把控件插入、删除、选区相关操作封装成自己的动作层
3. 对图片环绕、分页导出这类能力加开关

这样上游行为变化时，你只需要改一层适配。

## 6.2 不要一次性开放全部高级能力

建议按稳定度开放：

1. 先开放基础文本能力
2. 再开放简单图片、简单表格
3. 最后再开放复杂分页表格、环绕、复杂控件

## 6.3 保留备用方案

例如：

1. 图片环绕不稳定时，退回 inline 或固定布局
2. 复杂表格不稳定时，限制合并、分页或自动宽度
3. 控件删除链不稳定时，改走显式删除按钮而不是依赖键盘行为

---

## 7. 推荐的升级流程

每次升级 `canvas-editor` 前，建议固定做以下动作。

### 第一步：看上游 issue

重点看：

1. 你的核心使用模块
2. 最近新开的 bug
3. 最近关闭但可能影响你的修复

### 第二步：看仓库内重构文档

重点看：

1. `table-refactor-*`
2. `draw-refactor-*`
3. 性能方案文档

目的不是全部读完，而是确认：

1. 当前主链是否正在大改
2. 这次升级有没有碰到你在用的能力边界

### 第三步：跑你自己的最小回归

最低建议覆盖：

1. 输入
2. 删除
3. 光标移动
4. 拖选
5. 表格插入
6. 表格前后编辑
7. 图片插入
8. 导出或打印

### 第四步：决定是否升级

不要把升级当成“默认立刻跟进最新版本”，而是分三种情况：

1. 当前版本稳定且上游高风险链路正在重构：先不升
2. 你依赖的 bug 在上游刚修：做定向验证后再升
3. 只是普通功能增强，不影响你：可以延后

---

## 8. 推荐的个人执行清单

你现在就可以做的事：

1. 收藏上游 issues 首页和几个关键词搜索
2. 在自己项目里建一份“已知风险表”
3. 把表格、控件、图片、导出这些能力包一层适配
4. 先做一组最小回归页面
5. 以后每次升级前只看和你相关的 issues

---

## 9. 结论

你不是这个项目的作者时，正确用法不是去“治理上游 issue”，而是把上游 issue 当成风险情报源。

最重要的不是 issue 数量，而是从 issue 中提取三件事：

1. 哪些能力现在别重度依赖
2. 哪些能力升级前必须回归
3. 哪些能力需要你自己先包适配层和备用方案

如果按这个方式使用上游 issues，它们就不是噪音，而是你本地接入 `canvas-editor` 的预警系统。
